# Spec G2 — Fine-tuning LoRA/QLoRA

## Contexto
Com a base treinada do zero (G1), o lab precisa demonstrar adaptação barata:
treinar só um adaptador de baixo posto sobre pesos congelados, e a variante
QLoRA (base quantizada congelada + LoRA). LoRA e quantização NF4/int8 são
implementados **nativos** (sem peft/bnb) — o laboratório existe para demonstrar
a técnica, não só chamá-la. A quantização completa (medição de memória, 4-bit)
é o escopo da G3; aqui entra o mínimo para QLoRA funcionar.

## Objetivo
`lab-ia ajustar --base <run> --config <yaml>` aplica LoRA (ou QLoRA) na base G1
para adaptar o estilo a um subcorpus-tarefa; adaptador pequeno, inferência
funcional, comparação base × adaptado mensurável.

## Requisitos funcionais
- RF1: `NoLinear` envolve `nn.Linear`: `y = W₀x + BAx·(α/r)`; B zerado na init
  (adaptador começa identico à base); pesos da base com `requires_grad=False`.
- RF2: `aplicar_lora(modelo, r, alpha, alvos)` nos módulos lineares dos blocos
  (qkv/proj/fc1/fc2); `estatisticas_lora` reporta parâmetros treináveis/total.
- RF3: Salvar só o adaptador (`adaptador/lora.pt` + `adaptador/meta.json` com
  r, alpha, alvos, hash da config da base); `carregar_adaptador` reconstrói.
- RF4: `mesclar_lora(modelo)` dobra BA em W₀: saída idêntica (rtol 1e-5) e o
  modelo resultante não referencia mais os ramos LoRA.
- RF5: QLoRA: `quant_int8`/`quant_nf4` nativos (bloque 64, absmax);
  `--tipo qlora --bits 8|4` congela base quantizada + LoRA treinável.
- RF6: Runner de ajuste com as mesmas garantias da G1: métricas append-only,
  checkpoint do adaptador atômico, retomada por passo global determinístico.
- RF7: CLI `lab-ia ajustar` + `lab-ia gerar --run <ajuste>` (usa base+adaptador)
  + `GET /corre/{id}` já cobre o run de ajuste.

## Requisitos não funcionais
- RNF1: Adaptador ≤ 5% dos parâmetros da base (r=8 nos lineares de d=256).
- RNF2: Ajuste demo (500 passos, CUDA) ≤ 60s; testes em CPU ≤ 2 min.
- RNF3: Toda mensagem/user-facing em pt-BR.

## Critérios de aceite (Given–When–Then)
- CA1: Dado base G1 e subcorpus-tarefa, quando ajuste LoRA completa, então
  `loss_val(tarefa)` do adaptado cai ≥ 20% vs `loss_val(tarefa)` da base
  (baseline salvo no passo 0) e drift final−min ≤ 0.30 nats.
- CA2 (produto, medido no run real — pytest `-m slow`): dado `gerar` com prompt
  da tarefa, então a sobreposição de n-gramas 4 do texto gerado com o
  adaptador excede a da base em > 0.2. Evidência 2026-09-11: base 0.000 vs
  ajuste 1.000 (run g2-ajuste-ciencia, GPU). O teste de mecanismo em CPU
  verifica a métrica e a direção da perda na tarefa (micro não memoriza 4-gramas).
- CA3: Dado `mesclar_lora`, quando comparar logits base+adaptador vs mesclado,
  então idênticos (rtol 1e-4).
- CA4: Dado QLoRA 8-bit, quando treinar e gerar, então CA1 vale e os módulos
  quantizados + adaptador + escalas ocupam ≥ 2× menos bytes que os pesos fp32
  correspondentes (medição por módulo, auditável; embeddings ficam fp32 e são
  declarados fora da medição).
- CA5: Retomada de ajuste interrompido → métricas idênticas (<1e-6) ao contínuo
  (mesmo mecanismo da G1, testado em CPU).
- CA6: `pytest tests/g2/` verde sem GPU.

## Dependências e riscos
- Deps: G1 (run da base + tokenizer).
- R1: Alvos LoRA no nosso `qkv` conjunto (um Linear 3d) — aplicar nos três
  sub-espaços com o mesmo A/B? Decisão: LoRA no `qkv` inteiro (rank único),
  documentado no meta.json.
- R2: Estilo pode não mudar em tarefa fácil demais → tarefa escolhida com
  domínio distinto (capítulos específicos + discursos), medida por n-gramas.
