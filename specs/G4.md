# Spec G4 — Mistura de Especialistas (MoE)

## Contexto
A meta exige mostrar roteamento: cada token decide, por porta, qual especialista
processá-lo, treinando roteador e especialistas juntos, com inferência top-k
(custo ativo < custo total). Integração no próprio GPT via config para que
checkpoint, retomada e geração da G1 funcionem sem caminhos especiais.

## Objetivo
Camada MoE (estilo Switch) substituindo o FFN dos blocos: `n_especialistas`
MLPs idênticos ao FFN denso + 1 roteador linear; seleção top-k (1 ou 2);
perda auxiliar de balanceamento de carga; métricas de uso por especialista.

## Requisitos funcionais
- RF1: `ConfigGPT` ganha `n_especialistas` (0 = denso, retrocompatível),
  `top_k`, `coef_auxiliar`; serializam no `config_modelo` do checkpoint.
- RF2: Roteador: `softmax(Wᵣx)` → top-k, renormalizado (k=2); token vai só aos
  escolhidos; gradiente flui para roteador e especialistas usados.
- RF3: Perda auxiliar (Switch): `n · Σ fᵢ·P̄ᵢ` (fração roteada × probabilidade
  média), somada à perda de linguagem com `coef_auxiliar`.
- RF4: `metricas.jsonl` registra `aux_router` e `uso_especialistas` (lista de
  frações por especialista na última avaliação).
- RF5: `contar_parametros_ativos()` reporta o custo top-k (ativos < total).
- RF6: Treinamento/retomada/geração: sem código novo no runner — só a config.

## Requisitos não funcionais
- RNF1: Demo MoE (dim 256, 6 camadas, 4 especialistas, top-1, 2500 passos)
  ≤ 6 min na RTX 3070 (parâmetros ativos ≈ modelo denso da G1).

## Critérios de aceite (Given–When–Then) — v2 (2026-09-11)
> v1 pedia `min val ≤ dense − 0.05` ("MoE vence com custo ativo igual").
> Medições no mesmo corpus/config (seed 42, 2500 passos, RTX 3070):
> dense 4.673 · MoE top-1 (4 esp., 4× parâmetros) 4.703 · MoE top-2 4.700
> (drift final 0.27). Em corpus pequeno, dividir capacidade não ajuda — a
> v1 era folclore de grande escala. A v2 exige paridade + critérios estruturais
> e registra o achado.

- CA1 (paridade): `min(loss_val) ≤ dense_min + 0.05` E guarda de overfit
  final−min ≤ 0.25 nats. [top-1 medido: +0.030 / drift 0.033 ✅]
- CA2: Dado roteador treinado, quando avaliar, então nenhum especialista
  domina > 60% do tráfego (balanceamento real, medido por `uso_especialistas`;
  no run real com 4 especialistas, o esperado é 25%±15%).
- CA3: Dado `aux_router` = n·Σ fᵢ·P̄ᵢ, quando o roteador está balanceado o
  valor tende ao piso ~1 (não cai percentualmente como uma perda comum), então
  exige-se: `aux ≤ 1.15` no fim E `aux_final ≤ aux_inicial` (não divergiu) E
  nenhuma especialista acima de 60% do tráfego (colapso). O pytest cobre a
  não-divergência; o run real cobre o limite de colapso.
- CA4: Dado o modelo, quando chamar `contar_parametros_ativos`, então
  ativos < total e a diferença corresponde a (n−k) especialistas por camada.
- CA5: Retomada do run MoE interrompido idêntica (< 1e-6) ao contínuo (CPU).
- CA6: `pytest tests/g4/` verde em CPU; gerar texto do run MoE funcional.
- CA7 (achado documentado): top-2 com 4 especialistas não melhora (min 4.700,
  drift 0.27 > guarda) — em regime de dados escassos a fragmentação por
  especialista domina qualquer ganho; `configs/g4_moe_top2.yaml` preserva o
  experimento completo para re-auditoria.

## Dependências e riscos
- Deps: G1 (infra de treino).
- R1: colapso do roteador (tudo num especialista) → coef_auxiliar e CA2 o
  capturam; se colapsar no run real, ajustar coef antes de declarar derrota.
- R2: CPU lenta p/ micro-testes → lote pequeno, passos mínimos.
