# Spec B4 — Laboratório portátil (o app sobe o próprio núcleo)

## Contexto
O laboratório foi pedido portátil: instalar em outra máquina, abrir a janela e usar.
O que existia eram **dois artefatos separados**, cada um verificado por conta própria:

1. `ui/release/Lab-IA 0.1.0.exe` (71,2 MiB) — SPA + shell Electron, com
   `files: ["dist/**", "electron/**"]`: **não traz o núcleo Python**;
2. `.qwen/pyi-dist/lab-ia/lab-ia.exe` — núcleo congelado headless (64,6 MB de exe),
   provado rodando sem venv na G7.

Nada os unia. O `electron/main.mjs` calculava a raiz do laboratório como
`join(aqui, '..', '..')` — dentro do `app.asar` isso não aponta para lugar nenhum em
máquina de terceiros — e nenhum código subia o serviço. O rodapé prometia
"núcleo local em 127.0.0.1:8765"; quem subia era o usuário, na mão, num terminal.

## Requisitos
- RF1 (raiz): `LABIA_RAIZ` > pasta do usuário (`%APPDATA%\Lab-IA\lab`, gravável) em
  pacote > raiz do repositório em desenvolvimento. A pasta do app **não** serve: é
  somente leitura em vários cenários e vive dentro do asar.
- RF2 (núcleo): `LABIA_NUCLEO` > `resources/nucleo/lab-ia.exe` em pacote >
  `.venv\Scripts\python.exe -m labia.cli` em desenvolvimento > python do PATH.
- RF3 (semear): na primeira execução, copia `configs/`, `docs/` e `data/` iniciais do
  pacote para o workspace — **nunca sobrescrevendo** o que o usuário já tem.
- RF4 (subir): reaproveita um núcleo saudável na porta em vez de subir outro; senão
  lança o processo, registra saída em `.lab-ia/logs/nucleo.log` e espera `/saude`
  (até 180 s), distinguindo "morreu antes de responder" de "estourou o tempo".
- RF5 (encerrar): o núcleo morre junto com a janela (`window-all-closed` e `before-quit`).
- RF6 (montagem): `scripts/monta_portatil.py` junta `pacote/nucleo` e `pacote/semente` e
  **mede** o resultado; `ui/package.json` leva os dois como `extraResources`.
- RF7 (UI): a página Bancada mostra o estado do núcleo e tenta de novo a cada 2 s
  enquanto ele sobe, em vez de mandar o usuário abrir um terminal.

## Critérios de aceite
- CA1: a lógica de decisão é módulo próprio (`ui/electron/nucleo.mjs`) e tem teste em
  ambiente node: `ui/test/nucleo.test.ts` (19 testes) cobre raiz, comando, semente,
  espera de saúde e as quatro formas de falhar.
- CA2: os testes usam dublês injetados (`existe`, `lancar`, `buscar`, `dormir`, `agora`) —
  nenhum teste sobe processo nem espera 180 s de verdade.
- CA3: `scripts/monta_portatil.py --limpar` roda de ponta a ponta neste repositório e
  reporta o peso: **4,84 GB**, dos quais **4,08 GB são torch com CUDA**.
- CA4: `pnpm --dir ui build` limpo com as novas peças; `pnpm --dir ui test` verde.

## O achado que decide o empacotamento (medido, não estimado)
O núcleo congelado tem **4,84 GB** — e o alvo `portable` do electron-builder se
auto-extrai para `%TEMP%` a **cada execução**. Empacotar 4,84 GB assim significa
esperar minutos toda vez que o app abre. Os pesos medidos por dependência:

| pacote | tamanho | precisa? |
|---|---|---|
| torch (CUDA) | 4,08 GB | sim, para treinar na GPU |
| bitsandbytes | 117 MB | opcional (comparativo de quantização) |
| pyarrow | 79 MB | opcional (extra 'finetune', via datasets) |
| transformers | 39 MB | opcional no núcleo atual (nenhum import no core/labia) |
| numpy.libs + pandas + hf_xet + tokenizers | ~48 MB | tokenizers sim; o resto é do extra |

Três sabores possíveis, com o custo medido:

| sabor | tamanho aproximado | quando serve |
|---|---|---|
| **pasta + instalador (NSIS), CUDA** | ~4,9 GB instalado (comprime bem menos que isso) | máquina com GPU NVIDIA, uso real de treino |
| **pasta + instalador, CPU** | ~500 MB (troca o torch CUDA pelo CPU) | qualquer máquina, treino menor e mais lento |
| **portátil de arquivo único** | ~4,9 GB de auto-extração | só se a máquina destino não puder instalar nada |

A decisão é do usuário: o script mede, o README explica, e o código já funciona nos
três (a diferença é só qual núcleo vai dentro de `pacote/nucleo`).

## Riscos
- Empacotar não foi executado nesta sessão: `pnpm --dir ui package` baixa ferramentas
  (NSIS, winCodeSign) e **não há rede neste ambiente** — o mesmo motivo que impediu
  instalar matplotlib. O que está verificado é a montagem, a lógica e o build da SPA.
- Um núcleo CPU exige gerar o pacote com um wheel CPU
  (`pip download torch --index-url https://download.pytorch.org/whl/cpu`): é outro build, não
  uma opção de execução.
- `pacote/` fica fora do versionamento (5 GB não entram em git); `monta_portatil.py` é o
  reprodutor.
