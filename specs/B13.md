## 1. Contexto (autocontido — quem ler só este documento entende)

O Lab-IA é um laboratório local de IA em pt-BR, com núcleo em Python escrito no próprio
projeto (GPT do zero, BPE, LoRA/QLoRA, quantização int8/NF4, MoE, CoT/ToT, agentes) e uma
janela Electron + React com Design System próprio. O app sobe o núcleo sozinho, conversa com
ele por uma API HTTP local (`127.0.0.1:8765`) e encerra o processo que ele mesmo criou ao
fechar.

**O que a janela faz hoje** (7 abas): Painel, Detalhe do run (curva de perda), Bancada
(dados → config → *Treinar agora*), Executar (dispara YAML, mostra PID), Comparar (tabela,
diagnóstico, curvas), Trilha (10 lições com experimento rodável), Eventos, Design System.

**Base verificada:** 291 testes pytest (1 pulado) e 54 de UI, verdes. Treino de referência de
2,6 M parâmetros: 22,9 s de relógio (14,1 s de laço) na RTX 3070. Modelo de lógica de 5,8 M
treinado do zero em 150 s: **80,0%** de acerto em problemas não vistos, **71,7%** no split de
fórmulas maiores.

**Lacunas medidas na janela:**

| lacuna | evidência |
|---|---|
| não mostra o log do treino | `GET /execucoes/{chave}/log` existe e nunca é chamado pela UI |
| o Painel não se atualiza sozinho | `Painel.tsx` carrega uma vez, com botão "↻ Atualizar" |
| não há como ver o dataset | nenhuma tela lê `data/<id>/benchmark.jsonl` |
| não há como testar o modelo | nenhum endpoint de inferência sob demanda |
| não há como refinar pela tela | `ajustar` só existe na CLI |
| não há suporte a GGUF | llama.cpp não está instalado e nenhum modelo GGUF existe localmente |

## 2. Problema

O ciclo completo — escolher dados, configurar, treinar, acompanhar, medir e **conversar com o
modelo** — só existe em cinco comandos de terminal, e o meio do caminho (o treino
acontecendo) não é visível. A janela cobre o início e o fim, não o processo nem a
verificação.

## 3. Escopo

**Dentro:** uma área **Laboratório** com sub-abas encadeadas (Dados → Configurar → Executar →
Curvas → Testar → Medir), no formato de passos rodáveis; duas fontes de modelo-base (runs do
laboratório e modelos GGUF); log ao vivo para treino e benchmark; painel de exploração do CoT.

**Fora:** treinar modelos GGUF (llama.cpp não treina bem modelos grandes); servir API pública;
múltiplos usuários; autenticação; edição de dataset pela tela; comparação estatística com
múltiplas sementes (B10); pacote portátil (B11).
## 4. Vocabulário

| termo | significado exato |
|---|---|
| **run** | experimento em `runs/<id>/` com `estado.json`, `metricas.jsonl`, `ckpt/` |
| **dataset** | pasta `data/<id>/` com `manifesto.json`, corpus e (se for de raciocínio) `benchmark.jsonl` |
| **passo** | uma etapa do ciclo dentro de uma sub-aba, no formato de célula: mostra o comando equivalente, os parâmetros, um botão de rodar e a saída logo abaixo |
| **treinar do zero** | `lab-ia train` — tokenizer e pesos novos |
| **refinar** | `lab-ia ajustar` — LoRA/QLoRA sobre uma base congelada |
| **base** | o modelo de partida do refinamento: um run do laboratório **ou** um arquivo **GGUF** |
| **GGUF** | formato de pesos quantizados usado pelo llama.cpp; arquivo único, com tamanho em MB e nível de quantização (Q4_K_M, Q5_K_M, Q8_0) |
| **reasoning (declarado)** | o que o publicador do modelo afirma no nome/cartão do arquivo — é uma **afirmação**, não uma medição |
| **reasoning (medido)** | o resultado do benchmark deste laboratório rodado naquele modelo — é o único número que entra em comparação |
| **exploração** | painel em que você edita o texto do CoT e continua a geração. Serve para descobrir **onde** o modelo erra. Não é medição de acurácia e a tela diz isso |

## 5. Requisitos funcionais

### RF1 — Área Laboratório com sub-abas encadeadas (o "caderno")

**RF1.1** Uma área **Laboratório** com seis sub-abas, na ordem do ciclo de trabalho:
**Dados · Configurar · Executar · Curvas · Testar · Medir**.

**RF1.2 Formato de passo (célula).** Cada sub-aba é composta de passos numerados. Cada passo
tem, nesta ordem: título curto, o **comando equivalente da CLI** (texto monoespaçado,
selecionável e copiável), os parâmetros editáveis, um botão **Rodar** e o **resultado logo
abaixo**, que permanece na tela. Copiar o comando é o caminho de saída: quem quiser repetir
fora da janela não fica preso.

**RF1.3 Ordem visível.** A numeração dos passos deixa claro o que vem antes do quê, e um
passo que depende de outro mostra o que falta ("rodar o passo 2 antes"). Nenhum passo fica
bloqueado em silêncio.

**RF1.4 Estado por passo.** Cada passo tem um estado explícito: *não executado*, *rodando*,
*concluído* (com o resumo do resultado) ou *falhou* (com a mensagem e o conserto).

**RF1.5 Acompanhamento independente.** Fechar e reabrir a janela não perde o que já foi
rodado: o estado dos passos é reconstruído do disco (runs, datasets, execuções vivas).

### RF2 — Dados e base do experimento

**RF2.1 Sub-aba Dados.** Lista os datasets (id, itens de treino, itens de benchmark, idioma,
tokens aproximados, famílias), mostra o **manifesto** (procedência, parâmetros, sha256) e um
**navegador de itens** com enunciado, CoT e resposta, com filtros por família e split, busca
textual e navegação anterior/próximo. Os itens de lógica aparecem aqui como qualquer outro
dataset — não há tela especial de lógica.

**RF2.2 Fonte da base.** No modo refinar, a escolha da base tem duas origens, em abas
separadas, com avisos honestos:

| origem | o que mostra | honestidade exigida na tela |
|---|---|---|
| **runs do laboratório** | id, parâmetros, dispositivo, acurácia **medida** quando existir | "medido: 80,0% em lógica (60 itens, 13/09)" ou "não medido" |
| **modelos GGUF** | arquivo, tamanho em MB, quantização (Q4_K_M e afins), e a etiqueta de reasoning **declarada pelo publicador** | rótulo explícito: "reasoning: **declarado** pelo publicador — não medido aqui" e um botão **Medir agora** que roda o benchmark e transforma a declaração em número |

**RF2.3 Os três estados, agora com duas origens.** Ao lado de cada base: *treinado em
raciocínio* (a origem dos dados do run aponta para um dataset com `benchmark.jsonl`),
*medido* (existe relatório de benchmark, com data e número) e *declarado* (só para GGUF, e
sempre marcado como afirmação de terceiro). Uma base pode ter mais de um; a tela nunca funde
os três num selo só.

**RF2.4 Configuração do modelo.** Preset (com descrição), arquitetura (`GPT-2` ou
`moderna` com RMSNorm/RoPE/SwiGLU/GQA, e MoE quando fizer sentido) e sobrescritas de dim,
camadas, cabeças, janela, lote, passos, lr, abandono. No modo refinar, os campos de LoRA
(`r`, `alpha`, `tipo` lora|qlora, `bits` 8|4).

**RF2.5 Estimativas antes de rodar.** Parâmetros totais e ativos, VRAM aproximada, épocas e
tempo previsto — os mesmos números do `lab-ia novo`.

**RF2.6 Validação imediata.** Configuração impossível é recusada antes de enviar, com a
mensagem que diz o conserto (`dim (100) precisa ser divisível por cabecas (8)`,
`RoPE precisa de dim_cabeca par`, `warmup precisa ser menor que passos`).

**RF2.7 Revisão do YAML.** O passo final da sub-aba Configurar mostra o YAML gerado, editável,
antes de treinar.

### RF3 — Executar com log ao vivo (treino **e** benchmark)

**RF3.1** Treinar, refinar e medir disparam **execuções** (processo próprio), com chave, PID
e log em `.lab-ia/logs/<chave>.log`.

**RF3.2 Log ao vivo** para os **dois** casos: as últimas ~200 linhas, atualizadas a cada 2 s,
monoespaçadas, com rolagem, sem reformatação.

**RF3.3 Barra de progresso** lida de `runs/<id>/estado.json` (passo/total), com tempo
decorrido e restante.

**RF3.4 Perda ao vivo** (treino): última perda de treino e de validação, com sparkline.

**RF3.5 Progresso do benchmark:** "item 37 de 60" e a acurácia **parcial** acumulada,
atualizada conforme os itens saem — dá para ver se o modelo está indo bem antes do fim.

**RF3.6 Retomada de tela.** Fechar e voltar durante uma execução religa barra, log e perda.

**RF3.7 Parar e retomar.** Parar encerra o processo com confirmação; o run fica
`concluido=false` e o botão Retomar continua do último checkpoint. A tela diz isso ao
usuário em vez de deixá-lo adivinhar.

**RF3.8 Fila.** Havendo execução viva, avisa que a GPU é uma só e permite seguir, com o aviso
de que as duas vão competir.

### RF4 — Curvas e diagnóstico

**RF4.1** Perda de treino e de validação por passo, no gráfico SVG existente.

**RF4.2** Marcações: ponto de **melhor validação**, valor final e **deriva**. São os números
que dizem se o modelo decorou.

**RF4.3** Painéis secundários: lr, tokens/s, e uso de especialistas quando for MoE.

**RF4.4** Diagnóstico textual do run (`estavel`, `estagnado`, `deteriorando`,
`overfit`, `instavel`, `divergiu`) — o mesmo que `lab-ia comparar` produz, exibido
junto da curva.

**RF4.5** No refinamento, a curva da base aparece esmaecida ao fundo.
### RF5 — Testar o modelo (medir acurácia de verdade)

**RF5.1** Escolher o run (padrão: o último concluído).

**RF5.2** Enunciado com duas origens: **digitado**, ou **sorteado do dataset** (filtro por
família e split). No segundo caso a tela mostra o esperado e diz se acertou.

**RF5.3** Estratégia (direta ou CoT) e amostragem (temperatura, guloso, limite de tokens).

**RF5.4** Resultado em três blocos separados e rotulados: **texto gerado** (completo),
**resposta extraída** (o que o avaliador entendeu) e **veredito** (acertou / errou /
ilegível), com o esperado ao lado quando houver.

**RF5.5** Histórico da sessão: últimas 20 perguntas com resposta, acerto e estratégia, e a
contagem no topo. Fechar a tela perde o histórico, e a tela diz isso.

**RF5.6** Determinismo visível: com guloso ligado, a mesma pergunta dá a mesma resposta; se a
temperatura estiver acima de 0 com guloso ligado, a tela avisa que a temperatura será
ignorada.

### RF6 — Medir (benchmark)

**RF6.1** Escolher base/run, benchmark, split (teste ou difícil) e limite de itens.

**RF6.2** Resultado: acurácia global, **por família**, taxa de resposta válida, e até 10 erros
com o texto gerado — porque o erro é a informação.

**RF6.3** Comparar duas bases no mesmo benchmark, lado a lado, com a diferença em pontos
percentuais. É aqui que "reasoning declarado" de um GGUF vira número.

**RF6.4 Igualdade com a CLI.** Para os mesmos parâmetros (semente, split, limite), o número da
tela tem de ser **idêntico** ao da CLI. Divergir é bug da tela, não do modelo.

**RF6.5** O benchmark roda como execução, com log ao vivo e progresso parcial (RF3).
### RF7 — Explorar o CoT (o painel que você aprovou, com rótulo)

**RF7.1** Depois de uma resposta, o **texto gerado vira editável**. Você pode corrigir um
passo, apagar um trecho, trocar um valor e **continuar a geração a partir dali**.

**RF7.2** A tela mostra o **efeito da edição**: o texto final, a resposta extraída e, quando
o enunciado veio do dataset, se aquela continuação chegou à resposta certa.

**RF7.3 Rótulo obrigatório.** O painel é marcado como **exploração**, com a frase: "aqui você
está forçando o caminho (teacher forcing): o resultado não é a acurácia do modelo, é o que ele
faz quando o começo já está certo." Sem esse rótulo, o painel vira medição falsa.

**RF7.4 Botão "onde ele errou"**: compara o CoT esperado do dataset com o gerado, linha a
linha, e destaca o **primeiro passo divergente** — o atalho para achar o padrão de erro (por
exemplo: erra o operador depois de uma negação).

**RF7.5** O painel não grava nada que pareça métrica de modelo; o que ele produz vai para
`.lab-ia/exploracao.jsonl`, arquivo separado, para nunca contaminar relatório de benchmark.

```
+-- Lab-IA --------------------------------------------------------------------+
| Lab-IA  [Painel] [LABORATORIO] [Bancada] [Comparar] [Trilha] [Eventos] [DS]  |
+------------------------------------------------------------------------------+
|  LABORATORIO                                                                 |
|  +-[ Dados ]-[ Configurar ]-[ Executar ]-[ Curvas ]-[ Testar ]-[ Medir ]-+   |
|                                                                              |
|  SUB-ABA: CONFIGURAR                                       passo 2 de 3      |
|  --------------------------------------------------------------------------  |
|  1. Escolher os dados                                                  [ok]  |
|     dataset [logica-pq  v]  3000 treino - 300 teste - 200 dificil            |
|     $ lab-ia dados --listar                        [ copiar ] [ Rodar ]      |
|                                                                              |
|  2. Escolher o modo e a base                                       [rodando]  |
|     ( ) do zero       (o) refinar                                            |
|     base:  ( runs do laboratorio ) ( MODELOS GGUF )        <- abas           |
|       [x] logica-1       5,8 M   (o) medido: 80,0% em logica (60 itens)      |
|       [ ] livros-rapido  2,6 M   (o) treinado em rac.  ( ) nao medido        |
|       [ ] qwen2.5-1.5b-q4_k_m.gguf  986 MB  Q4_K_M                           |
|           reasoning: DECLARADO pelo publicador  [ Medir agora ]  (desab.)    |

|     $ lab-ia ajustar --config configs/logica-refino.yaml                     |
|                                                                              |
|  3. Ajustar e revisar                                                  [ ]   |
|     preset [equilibrado v]  arquitetura [moderna v]  r=8  alpha=16  lora v   |
|     ~5,2 M params - ~569 MB VRAM - ~1,2 min - 37 epocas                      |
|     [ ver YAML ]                                      [ GERAR CONFIG ]       |
|  --------------------------------------------------------------------------  |
|                                                                              |
|  SUB-ABA: EXECUTAR                                                           |
|  > treinando logica-refino-2   62%  ############---------  passo 1550/2500   |
|  perda trem 0,19 - perda val 0,19 - 1:20 decorrido, ~0:50 restante           |
|  +-- log ao vivo (2 s) -------------------------------------------------+   |
|  | [lab-ia] ajustando (lora, r=8) -> run 'logica-refino-2'               |   |
|  | passo 1550 loss 0.19 val 0.19 lr 0.0001 tokens/s 289000               |   |
|  +-----------------------------------------------------------------------+   |
|  [ PARAR ]  [ RETOMAR ]        execucoes vivas: 1  (benchmark tambem aqui)   |
+------------------------------------------------------------------------------+
```

**Sub-abas, em uma frase cada:** Dados (o que o modelo vai aprender) · Configurar (do zero ou
refinando, a partir de run ou de GGUF) · Executar (log ao vivo, barra, parar/retomar) ·
Curvas (perda, diagnóstico, melhor validação) · Testar (perguntar e ver o texto; editar o CoT
para explorar) · Medir (benchmark, por família, comparação de bases).

**Regra de forma:** todo passo mostra o comando equivalente, um botão de rodar e a saída logo
abaixo, que permanece na tela. É o "caderno": a ordem é o método, e o comando é a saída de
emergência para quem quiser repetir no terminal.
## 10. Riscos e decisões técnicas

| risco | decisão | alternativa descartada e por quê |
|---|---|---|
| "similar a um notebook": usar biblioteca pronta ou construir | **construir o formato de passo com o DS existente** (título, comando, botão, saída) | bibliotecas de notebook (Jupyter embutido, `nteract`) exigem instalação — **não há rede** (seção 12). O formato de passo entrega o essencial: ordem, comando visível, execução e resultado inline, com zero dependência nova |
| modelos GGUF como base | **catálogo em `modelos/` lido do disco**, com tamanho e quantização; sem llama.cpp, o item aparece mas fica desabilitado com o comando de instalação | esconder até o B8 pronto: o usuário não saberia que o caminho existe |
| "tem reasoning" em modelo de terceiro | rótulo **declarado** + botão **Medir agora** que transforma em número | aceitar a etiqueta do publicador: é afirmação, não medição |
| log ao vivo em treino e benchmark | polling de 2 s, um só componente reusado | SSE: mais código dos dois lados para 2 s de ganho |
| 3500 itens no navegador | paginação por `desde`/`limite` com leitura em streaming | carregar tudo: 1 MB por abertura |
| `metricas.jsonl` grande | endpoint de progresso leve | ler o arquivo inteiro a cada 2 s |
| edição do CoT contaminando métrica | arquivo separado `.lab-ia/exploracao.jsonl` + rótulo na tela | gravar junto: relatório de benchmark passaria a mentir |
| dois lugares medindo diferente | **CA7 exige igualdade com a CLI** | confiar em duas implementações: divergem em silêncio |
| treino e benchmark na mesma GPU | avisar e permitir | bloquear: medir sob carga é um caso legítimo |

## 11. Opinião do agente sobre a pergunta 4 (registro honesto)

Pergunta: *"o painel de teste deve permitir editar o CoT gerado e reenviar?"* — resposta do
usuário: *"acho que pode ser uma boa, você concorda ou discorda, sinceramente?"*

**Concordo, com uma condição.** A favor: é o instrumento que faltava para responder *por que*
o modelo erra. Os números de hoje dizem **o quê** (avaliação 91,7%, implicação 58,3%,
tautologia 66,7%), e não dizem onde quebra. Corrigir um passo do CoT e continuar mostra se o
erro é de **cálculo local** (ele erra o passo seguinte mesmo com o prefixo certo) ou de
**acumulação** (com o prefixo certo, ele acerta — logo o problema é carregar o estado da
conta). São dois diagnósticos com consertos opostos: o primeiro pede mais capacidade/mais
dados; o segundo pede formato ou curriculum. Sem esse painel, eu estaria adivinhando.

A condição: **o resultado não pode se misturar com acurácia.** Editar o prefixo é *teacher
forcing* — a partir dali o modelo não está resolvendo o problema, está continuando um texto
que você começou. Se isso entrar no mesmo relatório do benchmark, a métrica passa a medir a
nossa intervenção. Daí as três exigências: rótulo visível (RF7.3), arquivo separado
(RF7.5) e o alerta em CA15.

**Discordo de uma coisa:** do botão automático "onde ele errou" ser a única forma de
comparar. A comparação linha a linha é útil, mas o CoT esperado e o gerado podem divergir na
*forma* (agrupamento de parênteses, ordem dos passos) e ainda chegar à resposta certa. O
painel precisa mostrar a divergência **sem** afirmar que ela é o erro — o que decide é a
resposta final.

## 12. Bloqueios conhecidos (não são do design, são do ambiente)

| bloqueio | o que impede | o que dá para fazer sem ele |
|---|---|---|
| **sem rede** | instalar llama.cpp, baixar modelos GGUF, jupyter, qualquer biblioteca de notebook | todo o resto: treinar, curvas, testar com modelos do laboratório, medir |
| **sem llama.cpp** | usar GGUF como base de refino e inferência | o catálogo **lista** os arquivos; usar fica desabilitado com o comando de instalação à mão |
| **sem modelos GGUF no disco** | qualquer teste real do caminho GGUF | o caminho fica pronto e testado com um arquivo falso de estrutura válida |
