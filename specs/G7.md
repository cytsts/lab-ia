# Spec G7 — Empacotamento desktop

## Contexto
A barra exige "app desktop exportável". O núcleo Python roda do venv (documentado
no README); o app desktop empacota a camada visual com Electron Builder.

## Requisitos funcionais
- RF1: `pnpm --dir ui package` gera executável Windows **portable** em
  `ui/release/` (sem instalador de máquina, sem assinatura — uso local).
- RF2: O app empacotado abre a UI real e fala com o núcleo local em
  `127.0.0.1:8765` (README documenta `lab-ia servir`).
- RF3: O núcleo Python é empacotado com PyInstaller (`lab-ia.spec`, console
  headless) e o binário resultante executa de verdade — sem depender do venv.
- RF4: Linux/macOS: alvos configurados no electron-builder (build cruzado não
  testado nesta máquina Windows; documentado como não verificado).

## Critérios de aceite
- CA1: `ui/release/Lab-IA*.exe` existe, tamanho > 60 MB, e executa abrindo a
  janela com dados do núcleo (verificação por screenshot do empacotado).
- CA2: `scripts/verifica_pacote.py` sai com 0 falhas no bundle do núcleo:
  exe presente, nenhuma CRT do bundle mais antiga que a do sistema,
  `lab-ia.exe agentes` responde, e com `--cuda` o PID do exe aparece como
  processo CUDA em `nvidia-smi` durante uma geração real.
- CA3: O empacotamento é reproduzível por quem clona o repo: `lab-ia.spec` e
  `scripts/verifica_pacote.py` versionados (não podem morar fora do controle).

## Riscos
- electron-builder baixa ferramentas (nsis/winCodeSign) em tempo de build.
- PyInstaller + torch: coleção pesada; timeout de build aceitável ≤ 15 min
  (medido: 282 s nesta máquina).

## Revisão v2 — 2026-09-11: a "lacuna do PyInstaller" não existia

A versão anterior da RF3 previa falha ("se falhar neste ambiente, registre a
lacuna") e o fechamento usou essa saída. A causa registrada na época
("inicialização CUDA congelada") estava **errada**; o build era corrigível.

Diagnóstico medido, em quatro passos re-executáveis:

1. As 37 DLLs de `torch/lib` estavam **todas** no bundle, byte-idênticas às
   originais (sha256 `c10.dll` f5fcd07e9ac8 nos dois lados), e o wheel cu128 do
   Windows não tem `site-packages/nvidia/` — a coleção nunca foi o problema.
2. `T1`: réplica fiel de `_load_dll_libraries()` sobre `torch/lib` do venv →
   0 falhas. `T2`: a mesma rotina sobre `torch/lib` **do bundle** → 0 falhas.
3. `T3`: a mesma rotina sobre `torch/lib` do venv com a raiz `_internal` do
   bundle no caminho de busca → **c10.dll WinError 1114**. A falha se reproduz
   fora de qualquer exe congelado.
4. `T4`: idem a T3, retirando da raiz as 4 CRTs do redistributável → 0 falhas.

Causa: o PyInstaller resolve `msvcp140.dll` pela busca padrão, e nesta máquina
ela é atendida antes por outras instalações. O `COLLECT-00.toc` da build
quebrada registra a origem real:

```
('msvcp140.dll',    'C:\Program Files\Microsoft\jdk-11.0.16.101-hotspot\bin\msvcp140.dll')  # 14.16.27033, 2018
('vcruntime140.dll','C:\Python314\vcruntime140.dll')                                        # 14.42, Python do sistema
```

No app congelado `_internal` entra na busca de dependências de DLL e sombreia o
CRT do sistema; `msvcp140.dll` tem versionamento binário (sem retrocompat), e
`c10.dll` é compilada contra uma versão mais nova que a do JDK → a rotina de
inicialização falha. Nada a ver com CUDA.

Correção: `lab-ia.spec` filtra `a.binaries` e re-pincha as CRTs do
`System32`, tornando o build independente do PATH da máquina.

Armadilha conexa (por que a tentativa anterior não era reproduzível, mesmo com
boa vontade): o `.gitignore` herdado do template Python traz `*.spec` no bloco
do PyInstaller, que engolia `lab-ia.spec` em silêncio — o arquivo nunca pôde
entrar no versionamento. Agora há exceção explícita `!lab-ia.spec`, porque aqui
o spec é fonte do build.

Prova causal no artefato (`.qwen/mutacao_g7.py`, mesmo par mutate/restore):

| Estado do bundle | Verificador |
|---|---|
| íntegro (sha `7c26614e1d733892`) | rc=0, 0 falhas |
| `msvcp140.dll` do JDK recolocado (sha `c8f1fd703f67c2b3`) | rc=1, **2 falhas**: C2 + C3 `WinError 1114` |
| restaurado do System32 (sha volta a `7c26614e1d733892`) | rc=0, 0 falhas |

Evidência do bundle consertado (`.qwen/pyi-dist3/lab-ia`):

```
OK C2 msvcp140.dll 14.51.36247.0 (sistema: 14.51.36247.0)   # idem VCOMP140, vcruntime140, vcruntime140_1
OK C3 `agentes` respondeu (rc=0, 60 linhas)
OK C4 PID 28732 apareceu como processo CUDA no nvidia-smi durante a geração
=== resultado: 0 falha(s) ===
```

O `evaluate_model` rodado pelo exe congelado escreveu em `.lab-ia/eventos.jsonl`
(`2026-09-11T21:48:36+00:00`, `ok=true`, `duracao_s=2.29`, `min=4.6731`), que é
o mesmo mínimo da G1 — o binário independentemente do venv.

Regra nova: o verificador não aceita status auto-declarado porque ele *mede* a
versão de cada CRT no bundle e *observa* a GPU. O teste de regressão
`tests/g7/test_pacote.py` mantém o par mutação/controle com a CRT de 2018 como
fixture (`test_detector_discrimina_a_crt_sombreadora`).
