# Spec B3 — Bancada na API e na janela

## Contexto
B1 e B2 entregaram o ciclo pela linha de comando. Mas o laboratório foi pedido com
interface visual em TS/Electron — e a janela só sabia listar runs, ver métricas e
disparar um YAML que já existia. Sem contrato na API, o app portátil seria um
visualizador: quem quisesse trazer dados ou comparar runs teria de abrir terminal.

## Requisitos
- RF1 (`/saude`): estado do núcleo (versão, raiz, GPU, contagens, guias). É o que a
  janela usa para saber se o serviço subiu — e para mostrar "núcleo subindo".
- RF2 (`/datasets` e `POST /dados`): listar e preparar corpus próprio, com as mesmas
  guardas do CLI (id válido, teto de MB, fração de validação em faixa).
- RF3 (`/presets` e `POST /novo`): presets e geração da config comentada, devolvendo
  resumo legível, caminho, nome do arquivo, parâmetros, VRAM e épocas.
- RF4 (`/comparar`, `/comparar/relatorio`, `/comparar/curvas.svg`): comparação,
  relatório markdown e curvas como imagem.
- RF5 (`/guia/{nome}`): serve os markdown de `docs/` — o laboratório portátil leva o
  material de estudo junto, sem depender de internet.
- RF6 (`/execucoes/{chave}/log`): cauda do log de execução, para a janela mostrar o
  treino acontecendo em vez de só um PID.
- RF7 (janela): página **Bancada** (dados → config → treinar) e página **Comparar**
  (seleção de runs, tabela, diagnóstico, veredito e curvas).

## Critérios de aceite
- CA1: `tests/b3/test_api_bancada.py` verde (14 testes, CPU, sem rede), cobrindo RF1–RF6
  incluindo erros: 400 (id inválido, fração fora de faixa, preset desconhecido), 404
  (fonte/dataset ausente, guia inexistente, sem runs), 409 (config já existe), 422 (corpo vazio).
- CA2: a config gerada por `POST /novo` é aceita por `ConfigTreino.de_arquivo` sem ajuste
  manual, e aparece em `GET /configs` (a tela Executar consegue disparar).
- CA3: `/comparar/curvas.svg` devolve XML válido (`xml.etree`), com um `polyline` por run —
  sem matplotlib, porque o pacote portátil não deve depender de biblioteca gráfica.
- CA4: nenhuma rota aceita caminho arbitrário: `/guia/../../etc/passwd` e
  `/execucoes/../segredo/log` são recusados.
- CA5: `pnpm --dir ui test` verde (44 testes) com cobertura das duas páginas novas:
  preparar dataset, gerar config, treinar na sequência, erro do núcleo como aviso,
  comparar só os runs marcados, tabela + veredito + curvas renderizadas.
- CA6: `pnpm --dir ui build` limpo (`tsc --noEmit` + vite) — a página compila no pacote.

## Decisões
- Endpoints síncronos para `/dados` e `/novo` (são rápidos: segundos) e assíncrono só para
  treino (`/execucao`), que é o que dura minutos.
- Nome de arquivo de config é devolvido separado do caminho (`arquivo_config`), porque a tela
  Executar só aceita nome dentro de `configs/` — evita o cliente montar caminho na mão.
- Curvas são servidas como SVG pronto; a UI usa `<img>` e não precisa de biblioteca de
  gráfico nenhuma.

## Riscos
- A API é local e sem autenticação (como já era): qualquer processo da máquina fala com
  ela. Toda escrita continua validada por id/caminho, mas isso não é fronteira de
  segurança contra código local malicioso — é o mesmo modelo do `servir` original.
- `POST /dados` aceita caminhos do disco: é o que permite escolher a pasta de textos
  pela janela. Um seletor nativo de arquivos (IPC do Electron) seria mais amigável.
