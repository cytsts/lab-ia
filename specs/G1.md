# Spec G1 — Treinamento do zero

## Contexto
O lab precisa provar seu núcleo: treinar um modelo de linguagem do zero em pt-BR,
com perdas convergindo, checkpoints e métricas registradas — tudo reproduzível e
retomável. É a fundação sobre a qual G2–G5 (fine-tuning, quantização, MoE,
raciocínio) operam.

## Objetivo
Tiny LM decoder-only (arquitetura GPT, ~5–15M parâmetros) treinado com BPE pt-BR
sobre corpus de domínio público, via CLI `lab-ia train` headless e API interna.

## Requisitos funcionais
- RF1: `lab-ia train --config <yaml> --run-id <id>` treina e grava em `runs/<id>/`:
  `config.yaml`, `tokens/` (vocabulário BPE), `ckpt/` (checkpoints), `metricas.jsonl`,
  `estado.json` (progresso retomável).
- RF2: Checkpoint a cada `salvar_a_cada` steps (padrão 200), atômico (escreve `.tmp`
  → rename). `metricas.jsonl` é append-only com `loss_trem`, `loss_val`, `lr`, `step`,
  `tokens_s`, `tempo_s`, `timestamp`.
- RF3: Retomada: `--retomar` continua exatamente do último checkpoint (mesmo step
  seguinte), mesma seed reprodutível.
- RF4: Dataset: 95/5 trem/validação do corpus; seed de split fixa na config.
- RF5: Config: `dim`, `camadas`, `cabecas`, `janela_ctx`, `lote`, `passos`, `lr`,
  `warmup`, `peso_decay`, `grad_clip`, `seed`, `dispositivo` (`auto` usa CUDA se houver).
- RF6: `lab-ia gerar --run <id> --prompt "..."` gera texto de amostra do último ckpt.
- RF7: API interna (FastAPI): `GET /corre/<id>/metricas` devolve série p/ UI (G6).

## Requisitos não funcionais
- RNF1: Execução completa da demonstração ≤ 10 min em CPU; ≤ 3 min na RTX 3070.
- RNF2: Zero dependência de rede após preparação do corpus (tudo local).
- RNF3: Mensagens/logs do núcleo em pt-BR; identificadores de código em inglês.
- RNF4: IO pensado para SSD: escrita de checkpoint fora do laço crítico quando possível.

## Critérios de aceite (Given–When–Then) — v2 (2026-09-11)
> v1 pedia `loss_val_final < 0.60 × loss_val do 1º eval`. Medição real (run
> g1-treino-zero, 4000 passos, CUDA) mostrou a barra inatingível: o 1º eval já é
> posterior a ~60% da queda disponível, e o piso físico do corpus (~nats/token
> literário pt-BR séc. XIX) torna 0.6× fisicamente impossível. A v2 é mais
> difícil e verificável: duas condições independentes, uma de sinal e uma de
> regularização.

- CA1a (sinal): dado o baseline salvo em `metricas.jsonl` no passo 0 (modelo
  aleatório + `entropia_unigram`), quando o treino completa, então
  `min(loss_val) ≤ entropia_unigram − 1.5 nats` e `loss_val(20) < loss_val(0)`.
- CA1b (sem overfit): `loss_val_final − min(loss_val) ≤ 0.20 nats` nos últimos
  20% dos passos.
- CA2: Dado um run interrompido no passo N, quando reiniciado com `--retomar`,
  então produz métricas **idênticas** (tolerância < 1e-6) às do run contínuo de
  mesmo total, passo a passo (determinismo testado em CPU).
- CA3: Dado treino concluído, quando `lab-ia gerar`, então devolve texto não
  vazio, com caracteres alfabéticos, decodificável com o vocabulário salvo.
- CA4: Dado `metricas.jsonl`, quando lido, então contém o registro de baseline
  (passo 0, com `entropia_unigram`) + ≥ 1 registro por avaliação, em ordem, e é
  a fonte exclusiva de curva de perda da UI.
- CA5: Dado testes `pytest tests/g1/`, quando executados, então todos passam
  sem GPU.

## Dependências e riscos
- Deps: S1 (venv+deps), S2 (corpus).
- R1 (materializado, resolvido): v1 com janelas não sobrepostas ⇒ ~117 epochs de
  memorização (val subiu 4.99→6.04). Corrigido com `stride` deslizante (128).
- R2: Corpus pequeno (886KB) limita o piso de perda — por isso CA1 é relativa à
  entropia unigram medida, não a número absoluto.
- R3: Reproduzibilidade CPU vs GPU difere por kernels ⇒ teste de retomada roda só
  em CPU (igualdade estrita).
